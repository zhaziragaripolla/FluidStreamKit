A screen for every request you never built one for.

Your app has screens for the things you planned. FluidStreamKit handles the things you didn't: an AI agent builds the screen from your own components, for whatever the user just asked.

How it works

You build components once. The agent arranges them.

The agent sends a description of an interface using the open A2UI format. FluidStreamKit renders it with your views as it streams in.

Preview · working

1. Register your components

Start from the standard set (text, rows, cards, buttons, inputs) and add the views your app already has.

  • Each component decodes its properties into your own type.
  • A component with a standard name replaces the standard view.
  • Anything unknown shows a fallback, never raw JSON.
import FluidStreamHostUI

var catalog = A2UICatalog.basic
let schema = A2UIComponentSchema(name: "HotelCard", version: 2)
catalog.register(schema) { context in
    if let hotel = context.props(as: Hotel.self) {
        HotelCard(hotel)            // your existing view
    }
}
Preview · working

2. Tell the agent what your app can render

An agent can only compose from components it knows about. The catalog describes itself, so that description never drifts from your code.

  • A manifest lists every component, its properties and its version.
  • One call turns it into instructions for the agent's prompt.
  • The agent is limited to your approved pieces. It can't invent a button.
let manifest = catalog.manifest(version: "5.0")

// Send this to your backend, for the agent's prompt:
let instructions = manifest.agentInstructions()

// "Only these components exist in this app.
//  - HotelCard (v2)
//      name: string, required
//      price: string
//  - Text (v1): A run of text. ..."
Preview · working

3. Render what it sends

Feed the agent's bytes in as they arrive. The surface appears piece by piece, with placeholders for parts still on the way.

  • Inputs bind to the agent's data, so a total updates as the user changes a field.
  • Taps come back as structured actions for you to send to the agent.
  • An older app version that lacks a component shows the fallback you declared.
let store = A2UISurfaceStore()
var decoder = A2UILineDecoder()

// As the agent's response streams in:
for try await chunk in agentBytes {
    store.apply(decoder.feed(chunk))
}

A2UISurfaceView(store: store, surfaceId: "main",
                catalog: catalog) { action in
    // .event: send it to your agent
}
Use cases

Where composing beats a fixed screen.

It fits when the right interface depends on the request and can't be known in advance.

Questions with no fixed shape

A comparison, a chart with a breakdown, a ranked list. Each needs a different arrangement.

"Compare these three on battery and camera."

Forms built as it goes

The agent asks only what's relevant, with the right input for each question.

A return request, a claim, a booking with options.

Results from many tools

An assistant connected to dozens of services can show each result sensibly, without a hand-built card for every one.

A new tool is usable the day it's added.

Step-by-step tasks

A recipe with timers, a guide with checkboxes, a study session with a quiz.

Built for this task, then gone.

Review before acting

A summary of what the agent is about to do, different for every action, for the user to approve.

"Cancel this, and move $200 to savings."

Where a fixed screen is better

  • The answer always has the same shape
  • People use it constantly
  • Brand and polish matter most
  • The wording is regulated

The engine underneath · released

Streaming is a frame-budget problem. We measured it.

Long answers and arriving components both have to fit in a frame. The v1 engine buffers off the main thread and renders once per display refresh. It's useful alone, for any chat screen in Swift.

FluidStreamKit2.3 ms/s
